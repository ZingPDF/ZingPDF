# Verify full-page document OCR on Linux

This example generates five small synthetic PDFs and checks PDFium page rendering followed by real native Tesseract OCR. The corpus contains a digital header over a raster scan body, a page made from three separate scan tiles, a page with `/Rotate 90`, clean printed English rendered as an image, and a selectable vector-text page. The mixed page requires full-page OCR so an embedded header cannot hide the raster body. The vector page must use embedded text and must not invoke OCR.

The example implements `IOcrEngine` with the installed `tesseract` executable. It writes each rendered PNG to a unique temporary file, limits each OCR child process to 20 seconds, uses Tesseract orientation detection for the rotated page, kills the process tree on cancellation, drains redirected output, and removes the temporary image. It does not use the `Tesseract` NuGet wrapper; this acceptance run therefore verifies PDFium and the OS Tesseract binary, not the wrapper's native-library resolver. OCR output is retained in the synthetic run evidence. Worker logs contain only the case summary and failures, not page text.

Run from the repository root on a Linux Docker host with PowerShell 7 and Python 3.12:

```powershell
python -m pip install pypdf==6.10.0
./scripts/verify-document-workflow-linux.ps1
```

The script builds with the .NET 10 SDK because the source generator uses C# 13, then publishes a .NET 8 app into Debian bookworm slim. The image installs Tesseract and English plus orientation trained data during build. The worker has no network, a read-only root, UID/GID 1654, no Linux capabilities, `no-new-privileges`, 4 CPUs, 8 GiB memory, 256 processes, 256 MiB shared memory, and a 512 MiB temporary filesystem. Its `timeout` supervisor enforces a 60-second wall deadline. The app requests cancellation at 55 seconds and each OCR process has its own 20-second bound. The worker captures cgroup limits, package inventory, Tesseract version/languages, trained-data SHA-256, and the Linux x64 PDFium binary hash.

The wrapper saves input PDFs, OCR text and metrics, PNG previews, hashes, timings, independent-verification output, Docker image identity, and container configuration under a new `.tools/document-workflow-linux/<run-id>` directory. It keeps partial evidence when the worker or verifier fails. After the real corpus run, it starts a deliberate stall under the same GNU `timeout` supervisor with a three-second probe limit and requires exit code 124 within 20 seconds; this checks the timeout mechanism without waiting for the production 60-second limit. A retry builds and runs a new uniquely named container and volume; it does not reuse previous evidence. For a release candidate, provide approved immutable SDK/runtime image digests and exact Debian package versions with `-SdkImage`, `-RuntimeImage`, `-TesseractVersion`, `-EngDataVersion`, and `-OsdDataVersion`. Debian repositories may remove old package versions, so retain the approved image or use an approved package snapshot. Review and update the base images and OCR data hashes together, then rerun the entire corpus.

The independent Python verifier checks exact expected tokens, recomputes character error rate from captured output after Unicode normalization, case folding and whitespace collapse while preserving punctuation and digits, validates PDF page counts and SHA-256 values, checks preview PNG dimensions and hashes, validates the recorded cgroup and Docker limits and model/binary inventories, and confirms that image-only pages used rendered-page OCR while vector text used the PDF text layer. Every page must remain at or below 2% character error on this five-page synthetic corpus. It does not claim accuracy across a large document set, handwriting, degraded scans, other languages, hostile PDFs, JBIG2 images, CCITT-encoded image streams, or production concurrency. The sample is an acceptance harness rather than a production worker policy.
