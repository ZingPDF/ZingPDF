# ZingPDF Architecture

This is a compact map for future maintenance. Keep it factual and update it when module ownership or data flow changes.

## Major Areas

- `src/ZingPDF` contains the core PDF API, parser infrastructure, syntax object model, page editing, forms, drawing, text extraction, encryption, incremental updates, signing, redaction, metadata, image handling, and save pipeline.
- `src/ZingPDF.Fonts` contains standard PDF font metrics, AFM parsing, TrueType loading, and font metric providers.
- `src/ZingPDF.GoogleFonts` contains optional Google Fonts integration.
- `src/ZingPDF.OCR` contains OCR extraction helpers and Tesseract-backed OCR implementation.
- `src/ZingPDF.FromHTML` contains HTML-to-PDF conversion helpers.
- `src/ZingPDF.Templates` contains shared source and diagnostic abstractions for template renderer packages.
- `src/ZingPDF.Templates.LiquidHtml` contains Liquid HTML template rendering backed by Fluid and `ZingPDF.FromHTML`.
- `src/ZingPDF.InheritableSourceGenerator` generates code for inheritable dictionary properties.

## Public Surface

- `IPdf` is the main document contract.
- `Pdf` is the default implementation and owns document lifetime services, object collection access, parsing, document edits, save behavior, and high-level operations.
- Common public operations include page access/editing, form access, metadata, redaction, text extraction, watermarking, font registration, compression, encryption/decryption, document merging, signing, and save.
- Public page numbers are 1-based.
- Public XML documentation should state concrete behavior and important stream or PDF format constraints.

## Object Model

- PDF syntax wrappers live under `src/ZingPDF/Syntax`.
- Low-level PDF values include names, numbers, strings, arrays, dictionaries, streams, indirect objects, trailers, cross-reference structures, and page tree dictionaries.
- Dictionary wrappers should be used where they exist. Prefer adding or extending typed wrappers instead of scattering string-key dictionary manipulation.
- `ObjectContext` and `ObjectOrigin` describe whether objects came from parsed input or user-created output.

## Parsing

- Parser infrastructure lives under `src/ZingPDF/Parsing`.
- Object, dictionary, file structure, cross-reference, content stream, and date parsers are covered by focused unit and integration tests.
- `ParserResolver`, parser interfaces, token readers, and object group parsing provide the parsing composition layer.
- Avoid one-off string parsing for PDF syntax when an existing parser or token reader can be extended.

## Save And Incremental Updates

- Default save behavior appends an incremental update.
- `RemoveHistoryAsync()` switches saving to a fresh rewrite that keeps only latest live objects.
- Save, encryption, decryption, signatures, xref generation, trailers, and object stream behavior are high-risk areas. Changes here need focused tests and usually integration or smoke coverage.
- The save pipeline expects writable, seekable output streams and may reset/truncate output.

## Text And Fonts

- Text extraction lives under `Elements/Drawing/Text/Extraction`.
- Font dictionaries and text encodings live under `Text`.
- Standard and embedded font metrics are supplied by `ZingPDF.Fonts`.
- High-level standard font registration currently supports WinAnsi text fonts and excludes Symbol/ZapfDingbats.

## Forms And Annotations

- High-level form APIs live under `Elements/Forms`.
- AcroForm and field dictionaries live under `InteractiveFeatures/Forms`.
- Widget and appearance stream dictionaries live under `InteractiveFeatures/Annotations`.
- Form filling, flattening, appearance streams, and signature fields depend on both high-level wrappers and low-level PDF dictionaries.

## Tests And Fixtures

- Unit tests are in `tests/ZingPDF.Tests.Unit`.
- Integration tests are in `tests/ZingPDF.Tests.Integration`.
- Smoke tests are in `tests/ZingPDF.Tests.Smoke`.
- Shared test helpers are in `tests/ZingPDF.Tests.Common`.
- Performance benchmarks are in `tests/ZingPDF.Performance`.
- Fixtures live under `tests/TestFiles` and include PDF, image, HTML, and font inputs. Treat fixture files as intentional binary assets.

## Website And Documentation

- The product website is a static site in `website`.
- `website/docs.html` is curated by hand.
- `website/api` is generated by DocFX from XML docs and source metadata.
- Package README files live in `docs/packages` and are packed into NuGet packages.
- Public-facing website copy follows `website/STYLE_GUIDE.md`.

## Release Flow

- `Directory.Build.props` owns `VersionBase`.
- `scripts/prepare-release.ps1` calculates release metadata and updates `CHANGELOG.md` and `Directory.Build.props`.
- `.github/workflows/release.yml` builds, tests, packs, tags, creates a GitHub release, and can publish packages to NuGet.
- Performance workflows produce artifacts under `artifacts/performance`.
